# Property access settings — Slice 12

Administrators can prepare each property's separate shared-entrance, fixed-room,
and vacancy codes. `FIXED` means one room code is reused; `ROTATING` reserves a
vacancy code for periods with no following guest. There is no invented default:
properties with no settings return version `0` and `roomMode: null`.

This slice only stores administrative settings. It does not change a physical
lock, generate reservation codes, publish codes through staff/guest links, send
messages, or change existing QR access. Later slices must distinguish a prepared
code from confirmation that the physical lock has actually been changed.

## Routes and concurrency

- `GET /admin/properties/:id/access-settings`: property and configuration metadata.
- `POST /admin/properties/:id/access-settings`: save selected mode and code changes.
- `POST /admin/properties/:id/access-settings/reveal`: reveal one stored code.

All three require the existing active administrator session, and all responses
(including validation/authorization failures) have `Cache-Control: no-store`
through the existing middleware. Mutations and reveal requests are throttled.
Saving rechecks the active administrator inside a serializable transaction.

Save body: `expectedVersion`, `roomMode`, and optional `entranceCode`,
`fixedRoomCode`, `vacancyCode`. An omitted code preserves its value; `null`
explicitly removes it. A string replaces it. Strings accept 1–32 ASCII digits,
`*`, and `#` without trimming or numeric conversion, preserving leading zeros.
These are storage/input constraints; actual hardware compatibility is separate.
`FIXED` requires a saved/provided fixed room code. Entrance and vacancy codes may
remain unset so an administrator can prepare settings before supplying them.
Switching room mode preserves the other mode's stored code for later editing.

Reveal body: `expectedVersion` and `kind` (`ENTRANCE`, `FIXED_ROOM`, `VACANCY`).
Version mismatches return `409 ACCESS_SETTINGS_CHANGED`. Missing codes return
`404 ACCESS_CODE_NOT_SET`. Successful reveals contain only `kind`, `code`, and
`version`; ordinary reads and save responses contain presence flags, never code
values or encrypted envelopes. Parallel initial saves cannot overwrite each
other. The client should reload after uncertain save results rather than retry
an old version automatically.

## Secret storage and configuration

`PropertyAccessSettings` stores only per-field encrypted envelopes plus mode,
version, editor ID, and timestamps. AES-256-GCM uses a fresh 12-byte IV and
16-byte authentication tag. Authenticated context includes the property ID,
code kind, key ID, and a distinct `retreat-property-access:v1` domain. Moving a
ciphertext to another property/field or changing its envelope causes a safe
failure. Existing QR vault behavior is unchanged.

Use the already validated server-only `ACCESS_LINK_ENCRYPTION_KEYS` and
`ACCESS_LINK_ACTIVE_KEY_ID` configuration. No new environment variables are
needed. Missing keys or invalid envelopes fail closed for storing/revealing
codes. The public error filter intentionally returns the generic 5xx response;
it does not disclose cryptographic failure details. Unexpected database errors
are sanitized before the shared logger. Code values are never sent into Prisma
arguments, logs, URLs, report exports, or history snapshots.

Keep old keys when rotating the shared key ring: existing QR/private links AND
property codes depend on them until explicitly re-encrypted/replaced. Losing a
key makes its encrypted values unreadable. A database backup does not include
the external encryption keys. Do not put keys or real codes in Git or screenshots.

## Migration and release

`20261103000000_add_property_access_settings` is generated by Prisma 5.22's
offline `migrate diff` between the previous and updated schema. No hand-written
SQL, database connection, migration application, or backfill is involved.
Existing properties remain unconfigured; existing records are not rewritten.

The user applies it to the appropriate database:

```sh
# Local development only, applies the already generated pending migration
npx prisma migrate dev
npx prisma generate

# Production deployment only, after reviewing the release
npx prisma migrate deploy
```

`prisma generate` updates the generated client; it does not apply the migration.
No data backfill is required. Deploy the schema migration before serving the new
API. Verify the encryption key ring and the previously deferred origin HTTPS
configuration before entering real door codes. Local fixture testing does not
verify production transport, real devices, physical locks, or live data.
