# Reopening QR codes and personal links (Slice 11)

Property guest/staff QR and personal stay links can be reopened by an active
administrator after refresh or a later login. Reopen, copy, PNG download and open
do not rotate a token, extend expiry, increment a version or change old records.

## Compatibility and authorization

- Existing hash authorization remains unchanged. Existing printed QR codes and
  shared stay links keep their existing validity, expiry and revocation rules.
- Three nullable encrypted-token columns are additive. Old rows remain null;
  hashes cannot be reversed, so no automatic backfill or rotation is attempted.
- Status adds `canReopen`. It means a recoverable copy exists, not that access is
  currently enabled or that the server has a working decryption key. The UI also
  requires `enabled`; server retrieval independently checks current validity.
- Old valid hash-only credentials remain usable but cannot be reopened. The UI
  explains this. Only explicit replacement invalidates them. Importing an old
  saved original is outside this slice.
- GET `/admin/properties/:id/qr/guest/link` and `/staff/link` return the current
  `QrIssueDto`; GET `/admin/stays/:id/guest-link/current` returns the current
  `IssueStayGuestLinkDto`. Each is ADMIN-only and no-store, including errors.
- Personal retrieval requires active stay/property, matching stay revision and
  unexpired invitation. Property retrieval requires an active property and issued
  QR. Explicit revocation/replacement and staff reassignment remain authoritative.
- URLs are reconstructed from `FRONTEND_URL` and the same token. A future domain
  change needs its own migration/redirect plan; this does not preserve the original
  origin string if configuration changes.

## Server encryption configuration

The API uses Node's AES-256-GCM, a random 12-byte nonce and a 16-byte authentication
tag. Authenticated context binds each encrypted token to its purpose, record,
flow and current token hash. Retrieved plaintext is checked against that hash.
Opening tampered data, or opening data with a missing or wrong decryption key,
fails closed with a generic 503; it never triggers replacement. Missing sealing
configuration during new issuance has the narrow public error described below.
See [Node crypto](https://nodejs.org/api/crypto.html).

Add these **server-only** values to the local API `.env` and separately to the
EC2 API `.env` before rollout. Never use `VITE_`, commit the keys, share them in
screenshots or include them in logs. Use independent random keys for each environment.

```dotenv
ACCESS_LINK_ACTIVE_KEY_ID=primary
ACCESS_LINK_ENCRYPTION_KEYS='{"primary":"REPLACE_WITH_BASE64_32_BYTE_KEY"}'
```

The operator can generate a key locally with `openssl rand -base64 32`, then put
the result in the quoted JSON value. This document contains no runtime key.
Keep a secure backup of the keyring alongside the database recovery procedure.
Losing a key loses reopening for its encrypted rows; original QR/link access still
uses hashes. Do not regenerate the key on each restart or deployment.

Key IDs contain 1-32 letters, digits, `_` or `-`; 1-8 keys are supported. New
issuance uses the active ID. To change the active key later, retain old IDs/keys
for decryption of existing rows. This slice does not re-encrypt old rows in bulk.
Keys must be canonical base64 of exactly 32 bytes, independent of `JWT_SECRET`.
Both settings may be absent locally: existing access/status continue, but issuance
and encrypted retrieval fail. A partial/malformed pair fails startup. Production
Compose requires both and passes them only to the API, not the database/operator.

### Missing issuance configuration

If sealing configuration is absent, property QR rotation and personal-link
issuance return HTTP 503 with `ACCESS_LINK_ISSUANCE_UNAVAILABLE`. This dedicated
exception is thrown before either operation starts a database transaction, so
that failed request has not replaced the existing credential. The UI can retain
its existing preview and explain that server setup is needed, without locking
the action as an unknown write outcome. There is no automatic retry.

Only this typed exception receives a hardcoded public message. Generic 503s,
proxy/network failures, invalid tokens, decryption failures and unavailable old
keys retain their existing handling; they must not be classified as the same
known pre-write failure. Revocation also keeps its existing uncertainty handling.
No secrets or underlying crypto diagnostics are included in the public response.

Configure the keyring and restart the API to enable issuance. Refresh alone
cannot fix missing settings. A successful explicit replacement still invalidates
the previous QR/link; reopening a recoverable link does not replace it.

## Prisma migration and rollout

`20261030050000_add_recoverable_access_links` was generated by installed Prisma
5.22.0 using `migrate diff --from-schema-datamodel ... --to-schema-datamodel ...
--script`, comparing pre-change and updated schema files. Its SQL was not manually
authored. No database was connected or modified by generation. `prisma generate`
only updates the local client; it does not apply the migration.

User-run local steps, after configuring the local keyring:

```bash
cd /Users/john/Desktop/retreat-api
npx prisma migrate dev
npx prisma generate
```

The migration already exists; do not create another migration with the same change.
No backfill is needed. Restart the local API and verify it before the client.

For EC2, keep the existing user-controlled release process. Back up the database
and encryption keys, configure the API keyring, then prepare the committed API
release, apply committed migrations with `bash deploy.sh migrate`, and start it
with `bash deploy.sh up`. Those use `prisma migrate deploy` and migration-status
checks. Do not use `migrate dev` or reset in production. Deploy the API before the
client; avoid running old and new API versions concurrently for credential writes.
No EC2 action was performed as part of implementation.

## Verification and operational boundaries

Use a test retreat/stay: issue once, save its URL and rotation/version/expiry,
refresh, reopen and compare. Copy/download/open must leave those values unchanged.
Check legacy, inactive, expired, changed-stay, revoked and replaced states; test
non-admin requests and key failure. Staff handover must clear the encrypted staff
copy as well as its hash; guest QR/history remain unchanged.

The browser renders QR PNGs locally. Raw links and generated images stay in mounted
screen memory, never local/session storage or external QR services. Downloaded
files and copied links are access credentials; sharing them grants their scoped
access. Frontend/server/proxy telemetry must not capture response bodies or tokens.
This work does not configure CloudFront-to-EC2 HTTPS, which remains deferred.
